## НАСЛЕДИЕ V2.0 (добыто полем 2026-10-29 — не переоткрывать)
- Плагин `flutter_bluetooth_classic_serial 1.3.2`: `_bt.connect()` возвращает `true` ДО готовности RFCOMM-сокета (~1–1,5 с, `socket.connect()` в фоновой корутине); `sendData` до готовности кидает `NOT_CONNECTED`. Поэтому после `connect()` обязателен `_waitForSocketReady()` (рукопожатие `AT\r` → ответ с `>`). Инициализация — только после него, и её результат проверяется (`okCritical >= 6` из 7 критичных).
- Подключение (v2.1): до 2 попыток «socket+рукопожатие», при отказе `socket.connect()` (событие плагина `status 'ERROR: ...'`) — досрочный обрыв рукопожатия и повтор с чисткой сокета; причина отказа — `BluetoothService.lastError` (молчаливых ошибок нет). Первый коннект после установки: плагин запрашивает разрешения, `PERMISSION_DENIED` — ожидаем, повторить после выдачи.
- Боевой init-набор (проверен рабочим проектом `lada_vesta_scanner v3.0.0` в автомобиле): `ATZ` → критичные `ATE0/ATL0/ATS0/ATH0/ATSP6/ATSH7E0/ATCRA7E8` → опциональные `ATAL/ATCAF1/ATFCSH7E0/ATFCSD300000/ATFCSM1`. `ATZ` на этом адаптере безопасен. Без `ATS0/ATH0` ответы приходят с пробелами и префиксом `7E8` — парсер срежет, но позиционные `byteOffset` ломаются молча.
- Старый рабочий проект подключался «лучше» не по существу: он глушил ошибки init, а работал за счёт сохранённого состояния ELM327 (питание от OBD-порта непрерывно) и либерального парсера. Лечение V2.0: рукопожатие + проверяемый init + честные ошибки.
- RPM (`010C`): СТРОГО `(A * 256 + B) / 4` — без деления на 4 все пороги ломаются.
- `010B` (MAP), `0142`, `0146` — НЕ поддерживаются (`7F 01 12`): не опрашивать, константы НЕ подставлять; в UI — «НЕТ ДАННЫХ». Напряжение — ТОЛЬКО из ATRV.
- `0104` (Load) — `A * 100 / 255`; используется вместо мёртвого MAP (нагрузка/зоны, расчёт воздуха БК).
- Блок 220001 (семейство 2200xx) читается в DEFAULT SESSION — `1003` перед чтением НЕ отправлять. Структура `220001` НЕ совпадает с KWP `6101`. **Реверс выполнен по дампу 2026-10-29 (МОНИТОРИНГ 220001):** подтверждено — `rpm@4` (2Б, /4), `ect@54` (-40), `ltft@27` ((A-128)*100/128); кандидаты — `stft@22`, `volt@1` (/10); TBD — `@3`, `@7` (УОЗ/дроссель?), `@21`, `@33`. Внесено в `m86_uds.json` (id `uds_*`).
- `22F190/187/188/191/195`, `222001..003`, `220401..003` → `7F 22 12` ДАЖЕ в extended session — не использовать (подтверждено дампом 2026-10-29).
- Mode 06 (`0621`) — ОТВЕЧАЕТ (`46 21 01 01 00 00 00 00 00 03`), но структура TBD: пропуски не хардкодить до интерпретации.
- Строка длины ELM (`010`/`043`) — точная длина payload; хвост `AA` — паддинг, `extractBytes` режет корректно (проверено на 0904 и 220001).
- Источник истины с 2026-10-29 — живой дамп автомобиля; более ранние гипотезы о структуре данных считать опровергнутыми.
- Транспорт = SPP, не BLE. `dispose()` сервиса-синглтона не вызывается из экранов.
